# Nettoyage des fixtures de recette001–024

Le script `scripts/cleanup-completion-fixtures.ts` prépare un plan local à partir du manifeste privé des **cinq dernières identités fictives**, du contrat de configuration et des inventaires des recettes. Il n’exécute aucun SQL. Les identités sont vérifiées par UUID et domaine fictif, les objets par propriétaire/annonce/nom ; une ancienne campagne n’est jamais adoptée.

Les clés étrangères et les colonnes propriétaires Storage ont été lues sur le projet courant pour préparer l’ordre de suppression. Les SQL générés utilisent un bloc `DO`, des tableaux UUID locaux, des contrôles de périmètre et du DML ; aucune table temporaire ou migration n’est créée. Une interaction avec un autre compte, un autre site, une autre annonce ou un objet d’archive exigeant le worker arrête la transaction. Les limites globales, la politique MFA, les buckets et leurs policies ne sont pas modifiés.

1. Après la fin des recettes, exécuter `npx tsx scripts/cleanup-completion-fixtures.ts`. Examiner `.data/completion-cleanup-plan.json` et les deux fichiers SQL privés générés. Les candidats d’aperçu PNG peuvent ne pas exister : ils restent bornés à trois noms dérivés de chaque source fictive.
2. Le coordinateur applique le fichier `.data/completion-cleanup-dependencies.sql`. Les dépendances sont supprimées avant leurs parents, y compris les événements d’audit liés aux cibles exactes même si leur acteur est nul. Les comptes Auth et leurs droits restent disponibles pour le nettoyage Storage.
3. Le coordinateur exécute `npx tsx scripts/cleanup-completion-fixtures.ts --storage --db-rows-removed`. Le plan relu doit avoir la même empreinte et les mêmes objets. Le script se connecte normalement aux seules fixtures, crée et vérifie son propre facteur TOTP modérateur, confirme l’absence des données applicatives, puis utilise **Storage SDK remove** sur les noms exacts. Il vérifie les listes après suppression, révoque son facteur et ferme uniquement ses propres sessions. Aucune clé de service ni suppression SQL de `storage.objects` n’est utilisée.
4. Le coordinateur applique `.data/completion-cleanup-auth.sql` après vérification de `.data/completion-cleanup-state.json`. Une garde SQL refuse cette étape tant qu’un objet Storage appartient à ces identités ou porte un nom exact du plan. Les cinq comptes sont ensuite retirés, avec leurs dépendances Auth en cascade.

L’état final doit être relu par le coordinateur : aucun des cinq comptes, de leurs annonces, des trois sites fictifs, des objets exacts, des jobs et des événements de recette ne doit rester. Exécution du 21 octobre 2026 confirmée par le coordinateur : dépendances supprimées par DML borné, 10 objets privés et 10 objets approuvés puis 2 originaux de scène supprimés par le SDK Storage ; les 6 aperçus candidats étaient absents. Le facteur TOTP de recette a été révoqué, puis les 5 identités Auth ont été retirées. Relecture finale après la recette026 annulée : 0 compte, 0 annonce, 0 objet Storage, 0 site canonique et 0 plan commun dans ce projet de recette auparavant vide ; obligation MFA toujours active. Voir [completion-cleanup.json](completion-cleanup.json).
